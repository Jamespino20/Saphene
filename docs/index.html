The Loop — why developers keep it running

One audit is a snapshot. The ledger turns it into a cycle: fix, verify, re-audit. Every change to your code's health is diffed against the last run. Click a step.

1

Audit — the panel files its review

Four reviewer personas (security, performance, business-flow, maintainability) examine the code in parallel. Every finding must quote the file verbatim — and the quote is re-verified by grep before the finding is believed. Findings land in a ledger with stable IDs.

$ npm run audit -- --repo . --update-ledger
2

Fix — prompts an agent can actually run

The markdown report gives every finding surrounding code, long-term impact, and the reviewer's open questions. Paste the fix prompt into Copilot, Cursor, Cline, or OpenCode — if a question changes the approach, the agent is instructed to ask you first.

npm run audit -- --repo . --report my-fixes.md
3

Verify — the patch can't silently break promises

After the fix, the claim ledger re-checks documented behavior against the new code, and the PR gate diffs verdicts against the committed baseline. A patch that makes a documented claim false fails the pull request — with the citation that proves it.

$ npm run review -- --claims srs.md --repo . --ledger .saphene/srs.ledger.json
4

Re-audit — rot becomes a diff

The next audit diffs against the ledger: fixed findings show as resolved, newly introduced ones as new, and previously-verified claims that stopped holding as drift. Code health stops being a vibe and becomes a changelog.

vs previous audit: 41 unchanged, 3 fixed, 2 new, 1 regressed
5

Forget about it — CI runs the loop for you

Two GitHub Actions ship in the repo: one verifies claims on every push and posts the verdict table, the other comments on every pull request with its drift delta. Add a cron trigger and the nightly audit watches the repo while you sleep.

on: push: [main] pull_request: schedule: [{cron: "0 3 * * *"}]

Six jobs it does on a normal repo

No special repo shape, no setup ceremony. Each job is one command.

Who is this for?

Four profiles, one common thread: someone wrote down what the code is supposed to do, and they want proof it still does.

Solo developers with an agent in the loop

You keep notes and specs so Copilot, Cursor, or Cline has context. Months later, some of those notes describe code that no longer exists. Point Saphene at your memory directory: every claim is re-verified against the working tree, and stale notes come back as drift with a citation instead of a hunch.

Capstone and SRS teams

Requirements become claims with clause numbers and requirement types, verdicts carry file:line receipts, and the traceability matrix exports to CSV or markdown. When an adviser asks for proof that requirement 4.3 is implemented, you hand over the citation.

Maintainers adopting unfamiliar code

Inherited a repo with more history than documentation? Run the panel before your first commit. Four reviewer personas file findings with verbatim quotes and paste-ready fix prompts, and the ledger you commit becomes the baseline every later audit is diffed against.

Teams that gate PRs on documented behavior

Commit a claims ledger and the review gate checks every pull request against it. A patch that makes documented behavior false fails CI with the line that proves it, so review starts from evidence instead of opinion.

Why not just a linter? Or an AI reviewer?

Because neither one remembers what it told you yesterday.

A linter

Checks style rules against the current file. No memory of your docs, no cross-file claims, no opinion on whether the code still matches what you wrote down. Nothing persists between runs.

An AI code reviewer

Reads your diff and gives a one-shot impression. Smart, but stateless: it never verifies what your README promised, and its review of this PR is forgotten by the next one.

Saphene

Verdicts with grep-verified file:line receipts, persisted to a ledger. Re-runs diff against the last one, documented behavior that stops being true fails CI, and the same engine answers your agent over MCP.
