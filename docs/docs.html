Documentation

Everything a developer needs to run Saphene on a real repository in under five minutes — and keep it running forever after.

Quickstart

git clone https://github.com/Jamespino20/Saphene.git
cd Saphene
npm install

# 1. scaffold a memory directory (or skip — point at any folder of .md files)
npm run init -- --memory-dir ./memory

# 2. write a claims file (see format below), then verify it against a repo
npm run bridge -- examples/matriflow-claims.md --repo D:/Projects/your-repo

# 3. audit the repo's code with the reviewer panel
npm run audit -- --repo D:/Projects/your-repo --update-ledger

# 4. run the self-test to confirm your install
npm test

No model key? Everything deterministic still works — extraction falls back to the heuristic parser and --no-model forces it anywhere.

Concepts

TermMeaning
ClaimA single testable statement extracted from memory, a spec, or a document — with 1–3 expected evidence strings: literal text that would appear in the codebase if the claim is true.
Evidence surfaceWhere the grep loop looks: the source file (memory mode), or target repos/files (bridge mode). --code-only restricts targets to implementation extensions so specs can't testify for themselves.
Verdictmatched (all evidence located) · partial (some) · unfound (none) · mismatch (contradicted). Every verdict carries a file:line citation.
LedgerPersisted verdicts with stable IDs (.saphene/ledger.json). Re-running diffs against it — the mechanism behind drift detection.
DriftA status regression between runs: something that was matched stopped being true. The ledger records what, when, and the citation that changed.
FindingAn audit observation from a reviewer persona: severity, category, verbatim quote (grep-verified), long-term impact, open questions, fix direction.

Claims file format

Saphene's heuristic parser reads structured claim blocks — and the model extractor outputs the same shape. One claim per - bullet, metadata lines below it:

- Expected delivery date is calculated from LMP using Naegele's rule.
  category: srs | srsClause: 5.3.2 | requirementType: functional | priority: mandatory
  evidence: calculateEDC, Naegele, lmp_date

Good evidence strings are literal and specific: identifiers, table names, function names, exact phrases. Bad evidence is paraphrase — the grep loop can't find what isn't written. Categories: fact, config, numeric, path, behavior, srs. Requirement types (for SRS claims): functional, performance, safety, security, interface, operational, constraint, quality.

Model configuration

Any OpenAI-compatible endpoint works. Create .env (gitignored):

MODEL_BASE_URL=https://generativelanguage.googleapis.com/v1beta/openai
MODEL_API_KEY=your-key
MODEL_NAME=gemini-3.5-flash
MODEL_FALLBACK=gemini-3.1-flash-lite

Calls retry with backoff (3× per model) and fall through the chain on repeated failure. Free tiers work — Saphene's own public CI runs on one. In GitHub Actions, set the key as the SAPHENE_API_KEY secret; the workflow writes .env from it automatically and runs heuristic mode when absent.

Ledger & drift

Claim IDs are deterministic hashes of source::text (audit findings: file::reviewer::title) — stable across runs and machines. Each ledgered run records status, citation, and timestamp; the next run diffs:

TransitionClassification
matched → partial / unfound / mismatchdrift (regression)
partial → unfound / mismatchdrift (regression)
unfound ↔ mismatchdrift (escalation)
unfound / partial / mismatch → matchedresolved
same statusunchanged

Drift exits nonzero — which is exactly why the GitHub Action can fail a build on it.

The audit panel

One model call per file returns findings from four independent reviewers, run three files at a time. Findings are only believed after their verbatim quote is located in the file by grep — otherwise they're demoted to partial and flagged. The report includes, per finding:

  • Receipt: the quote and file:line
  • Long-term impact: what rots, what compounds, what it costs later
  • Questions for the developer: what the reviewer would ask before fixing
  • Surrounding code: ±8 lines with line numbers
  • Fix prompt: paste-ready for any coding agent, with instructions to ask first and state assumptions

Reports default to audits/-.md; override with --out-dir or --report.

MCP setup

Saphene speaks Model Context Protocol over stdio — one server covers VS Code Copilot agent mode, Cursor, Cline, and OpenCode. Start it with npm run mcp and register it:

{
  "mcp": {
    "saphene": {
      "type": "local",
      "command": ["npx", "tsx", "/src/mcp.ts"],
      "enabled": true
    }
  }
}

Tools: saphene_bridge (claims file vs repo → verdicts), saphene_memory (memory dir vs repo → ledger diff + drift), saphene_verify (single file, memory or paper mode). Findings and verdicts return as structured JSON your agent can reason over.

GitHub Actions

Two workflows ship in .github/workflows/:

WorkflowTriggerBehavior
saphene.ymlpush, manualClones target repos, verifies both example claim sets, posts verdict tables to the job summary. Optional SAPHENE_API_KEY secret upgrades it to model extraction.
saphene-review.ymlpull_requestRuns the ledger-diff review against committed baselines and comments the delta on the PR. Drift fails the check.

For a nightly watch, add a schedule trigger: schedule: [{cron: "0 3 * * *"}] — the ledger diff means you only hear about what changed.

The continuous loop

The intended rhythm on a live project:

  1. npm run audit -- --repo . --update-ledger — baseline or refresh; findings ledgered
  2. Open the report, paste fix prompts into your agent, merge fixes
  3. npm test + the PR gate confirm documented claims still hold
  4. Re-audit — the ledger diff reports resolved vs new vs regressed
  5. CI re-verifies on every push; the memory write-back records what changed and when

Step 4 is the part nothing else gives you: code health as a changelog, not a vibe. A claim about your system that stops being true — whether it lives in your README, your agent's memory, or your own head — has an exit code now.

Exit codes

CodeMeaning
0All claims matched / no drift / no critical findings
1Unfound, mismatch, or drift present (review needed)
2Engine error — model required but unavailable

FAQ

How is this different from a linter or CodeRabbit-style review?
Linters check style rules; AI reviewers give one-shot impressions. Saphene persists a ledger with stable IDs, so its reviews diff across runs and commits, its verdicts carry grep-verified receipts, and it fails CI on documented-behavior drift — not on taste.

Why did my "matched" claim cite a TODO comment?
String evidence can't read negation — a comment saying "would implement X next" contains the words. This is why every verdict ships its citation: you're meant to glance at receipts. The audit panel's model reasoning layer is where semantic judgment lives.

Does it work without internet?
The deterministic engine (extract-from-blocks, grep loop, ledger, drift, PR gate, MCP) is fully offline. Only model-backed extraction and the audit panel need the endpoint.

What stops the audit from hallucinating?
Quotes must exist verbatim in the cited file — the grep loop checks every one and demotes failures. It's not perfect (a matching TODO comment taught us that), which is why receipts are the product.
